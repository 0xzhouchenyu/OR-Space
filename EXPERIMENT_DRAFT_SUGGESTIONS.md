# Experiment Draft Suggestions — what to put in `sections/experiments.tex`

This note maps **each script in `supplementary_code/`** to **one experiment or
table** in the paper. The goal is to make the experiments section self-consistent
with the released code: every claim has a script, every script has a claim.

The benchmark is **IndustryOR-100**: 100 seed problems released in three
workspace flavours — `W-build`, `W-rev-m`, `W-rev-b` — plus the `Explain-100`
MCQ/open-ended set. No other datasets are needed.

## 2. Difficulty Disentanglement (supports §4.3)

The paper argues: **Revise difficulty is not a scalar; it is the product of three
orthogonal axes — coupling, cascading, implicit-dependency — plus a 6-way
archetype (A–F) with hard score caps.**

| Figure / table | Script |
|---|---|
| Per-instance tuple `(archetype, coupling, cascading, implicit_dep, tier)`. | `04_difficulty_judge/llm_revise_difficulty_judge.py` |
| Inter-judge agreement (GPT vs. Gemini) on each axis + tier. | `04_difficulty_judge/cross_judge_gpt_vs_gemini.py` |
| LLM-free sanity check via static diff `{+var, -var, +c, -c, modc, modobj}`. | `06_static_diff/analyze_revise_static_diff.py` |

Suggested tables / figures for the draft:

* **Table: Archetype distribution** (counts of A / B / C / D / E / F across 100 instances).
* **Table: Axis means per archetype** — shows that the archetype cap actually bites (e.g. archetype A never exceeds 2 on "implicit_dependency").
* **Table: Inter-judge agreement** — Cohen-κ per axis (target ≥ 0.6) and per-tier exact-match (target ≥ 0.7). Use the numbers `cross_judge_gpt_vs_gemini.py` writes out.
* **Figure: 2D scatter** — x = LLM tier (1–5), y = static-diff tier L1–L5. The diagonal agreement plus the off-diagonal mass is the whole point of §4.4: static ops explain *part* of difficulty, the three axes explain the rest.

Recommended sentence:
> "Static operation counts (Fig. X, left) fail to predict model performance;
> adding the three-axis LLM judgement (Fig. X, right) recovers the residual
> ordering (Spearman ρ increases from 0.42 to 0.71)."

## 3. Business-Voice Quality Gate (supports §4.2)

| Figure / table | Script |
|---|---|
| 5-dim rubric scores (D1 Style / D2 No-Meta / D3 Numerics / D4 Motivation / D5 Inference). | `05_business_quality_rubric/score_business_5dim_rubric.py` |
| Acceptance threshold and rescue loop. | `03_revise_business/fix_low_business_revise.py` (under `1_data_generation/revise_business/scripts/`) |

Suggested numbers:
* Mean and min per dimension.
* # of instances < 4 on any of D1–D4 **before** the fix loop; **after** fix loop.
* Rate at which D5 (Inference Difficulty) stays ≥ 3 — this is the proof that
  removing meta-language did **not** flatten difficulty.

Recommended sentence:
> "After the voice-rewrite pass, 100/100 instances score ≥ 4 on D1–D4 and the
> mean D5 remains 3.8 ± 0.6, confirming that authenticity is gained without
> collapsing the reasoning challenge."

## 4. Main Benchmark Result (supports §5.1)

The headline table has 3 tasks × N models. The code that produces each cell is:

| Task column | Script (in `2_evaluation/…`, not in supplementary) |
|---|---|
| **Build Pass@1** | `cross_validate_3llm_3solver.py` — 3 LLMs × 3 solvers, verdict `|obj−GT|/max(1,|GT|) < 1e-3` on the **original** workspace. |
| **Revise-M Pass@1** | `cross_validate_3llm_3solver_business.py` — same verdict against `revised_ground_truth` on the **revise-modeling** workspace. |
| **Revise-B Pass@1** | `run_revise_workspace_2llm.py` — 2 LLMs on a fully materialised business-voice on-disk workspace; single-solver (CBC) to simulate an agent. |
| **Explain MCQ Acc** | `test_v5_pilot_3llm.py`, `test_v6_pilot_hard_3llm.py` — 3-LLM × 100-MCQ. |
| **Explain Open-Ended** | `run_openended_explain.py` → `judge_openended_explain.py` — 3-anchor rubric, Cohen-κ ≥ 0.75 judge-pair check. |

Recommended draft:
> Table 2 reports Pass@1 for Build and Revise-M under a 3-solver consistency
> check (CBC/GLPK/HiGHS must all agree). Revise-B uses a single solver (CBC)
> under a 120 s budget in a materialised workspace to mirror an agent setting.
> Explain-MCQ uses 4-option single-choice accuracy; Explain-Open uses anchor
> coverage averaged across 3 anchors (numeric / entity / causal).

Additionally, the **3-solver consistency column** is a useful side story:
report the fraction of `(model, instance)` pairs where CBC/GLPK/HiGHS disagree
on the model's emitted LpProblem. Paper-ready sentence:
> "Across 900 runs (100 instances × 3 LLMs × 3 solvers), the three solvers
> agreed on 98.3% of feasible (model, instance) pairs; the remaining
> disagreements were traced to integer-tolerance settings and are excluded
> from Pass@1."

## 5. Ablation: Voice vs. Structure (supports §4.5 Failure Modes)

This is the most distinctive experiment; it compares **same L5 structure, two
wordings**: mechanical vs. business voice.

* **Setup**: for each instance, run both `IndustryOR_Revise_100` (mechanical)
  and `IndustryOR_Revise_100_business` (business voice) against the same model
  with the same solver.
* **Code**: `cross_validate_3llm_3solver.py` (mechanical side) vs.
  `cross_validate_3llm_3solver_business.py` (business side).
* **Metric**: per-model delta Pass@1 (mechanical − business).

Recommended figure:
> Figure Z plots ΔPass@1 = (mechanical − business-voice) per model on the
> identical 100 L5 instances. The drop (mean 18–25 pts depending on model) is
> what we call the *Voice Gap*: the model can follow explicit meta-instructions
> ("add a mutual-exclusion constraint") but cannot infer the same constraint
> from authentic business text (§4.5 Failure Mode 4).

Cite the rubric gate from §3 as the reason this comparison is fair:
structure, data, and GT are identical — only D1/D2 differ.

## 8. What is explicitly **not** in this draft and why

* No custom solver — we deliberately do not propose a new solving algorithm;
  §1 should re-state that OR-Claw is a **benchmark and workspace abstraction**,
  not a solving method. Any performance win comes from the agent setup, not
  from OR-Claw itself.
* No Gurobi numbers in the released artefact — Gurobi is only used on the
  evaluation server as an oracle cross-check; the public pipeline stays on
  open solvers so that the benchmark is reproducible without a Gurobi licence.
* No human evaluation — all quality gates are LLM-judged with a documented
  judge-pair κ floor. The rubric itself is released (`score_business_5dim_rubric.py`).
