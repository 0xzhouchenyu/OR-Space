We are no longer preparing this electronic system for just one reference deployment. The program team now needs a single pre-deployment spare-part package that can be carried into two equally likely mission profiles: Scenario A, the patrol mission, and Scenario B, the assault mission. The same hardware setup has to go out the door for both cases, with no opportunity to add, remove, or swap spares after deployment, so the spare configuration must be robust enough to satisfy the logistics limits of both missions at once.

The system still consists of three component types, and the system is considered operational only when component 1, component 2, and component 3 all function properly. For each component i, the number of spares carried is an integer choice s_i taken from {0,1,2,3,4,5}, where s_i = 0 means only the base unit is present and s_i = k means k spare units of that component are installed or carried with it. The reliability of each component depends only on its own spare count and does not change between missions. In table_1.csv, the entries `Component_1_Reliability`, `Component_2_Reliability`, and `Component_3_Reliability` give R_1(n), R_2(n), and R_3(n) for each n in {0,1,2,3,4,5}. For any chosen configuration (s_1, s_2, s_3), the system reliability in Scenario A is SysRel_A = R_1(s_1) * R_2(s_2) * R_3(s_3), and the system reliability in Scenario B is SysRel_B = R_1(s_1) * R_2(s_2) * R_3(s_3).

What does change by mission is the logistics envelope. In general_parameters.csv, `unit_price_component_1`, `unit_price_component_2`, and `unit_price_component_3` give the yuan cost of one spare for each component type, while `unit_weight_component_1`, `unit_weight_component_2`, and `unit_weight_component_3` give the corresponding spare weights in kg. That means the total spare-part cost is s_1 * `unit_price_component_1` + s_2 * `unit_price_component_2` + s_3 * `unit_price_component_3`, and the total spare-part weight is s_1 * `unit_weight_component_1` + s_2 * `unit_weight_component_2` + s_3 * `unit_weight_component_3`. The patrol mission and assault mission each impose their own ceilings: `total_budget_scenario_A` and `weight_limit_scenario_A` for Scenario A, and `total_budget_scenario_B` and `weight_limit_scenario_B` for Scenario B. Because one common spare package must serve both missions, its total cost has to stay within both `total_budget_scenario_A` and `total_budget_scenario_B`, and its total weight has to stay within both `weight_limit_scenario_A` and `weight_limit_scenario_B`.

Since Scenario A and Scenario B are equally likely, the planning target is the expected system reliability, namely ExpectedReliability = 0.5 * SysRel_A + 0.5 * SysRel_B. In this case the two scenario reliabilities are numerically the same for any fixed spare package because the component reliability table is scenario-independent, but the feasible spare package is limited by having to clear both missions' budget and weight screens. Please refer to the corresponding CSV files in the data folder for the specific parameter values, and determine the spare counts s_1, s_2, and s_3 for the three components that give the highest ExpectedReliability while remaining acceptable for both Scenario A and Scenario B.
